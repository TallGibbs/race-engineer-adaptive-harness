Adaptive Harness: an agentic engineering team that learns from its own runs

An agentic engineering team (a data engineer, a statistician, and the lead role that writes the brief, named race_engineer in the code) whose harness learns from its own recorded runs and proposes changes to its own configuration. A fixed evaluator decides which changes are kept, and MongoDB Atlas, including Atlas Vector Search for lessons, is its memory. The harness is the product. Built on 2026-09-26 at the MongoDB hackathon for Statement One, Recursive Harnessing, and trialed on briefs built from public motorsport timing data (FastF1).

This project is unofficial and is not associated with the Formula 1 companies.

What it is

The claim under test: a harness that records its own runs can find the root causes of its defects in those records and change its own process so that it passes more checks on a fixed evaluation it cannot edit, without getting worse elsewhere. The design fits any analytics and engineering workflow where outputs must cite their evidence.

In the trial, the team writes two brief types:

  • venue_brief: how often Grand Prix races at a venue were interrupted by a safety car (SC) or a virtual safety car (VSC), with counts, rates, and 90% Wilson intervals.
  • race_audit: whether a given race had an SC, a VSC, or a red flag.

Every message, tool call, tool result, check, and decision is written to MongoDB Atlas. An improvement cycle (DMAIC: define, measure, analyze, improve, control) reads those records, proposes changes to the harness configuration, and keeps a change only if a fixed evaluator, running as a separate process, shows it passes more checks without regressions.

How it works

Three role agents work each case in one bounded discussion. The race engineer runs on Claude Opus 5.5; the statistician and the data engineer run on Claude Sonnet 5. The stages are fixed by the harness configuration:

Each case run has fixed budgets: 40 model calls, 60 tool calls, 900 seconds. The tools read public timing data through the open-source FastF1 library into a local cache outside the repository, with an as-of guard. The fixed evaluator is the only code that reads the answer key; it scores eight checks per run (E1 schema, E2 venue, E3 coverage, E4 indicators, E5 arithmetic, E6 disposition, E7 evidence, E8 budget).

How it improves

The harness improves its own process with DMAIC. An improvement agent (Claude Opus 5.5, fixed prompt) writes the text of each phase; code decides every tollgate. The cycle stops at the first tollgate that does not pass, and the stop is recorded as the outcome.

The two pilot arms isolate the configuration change from the lessons: memory_only is the current version with the new lessons (snapshot M1), and candidate is the proposed version with the same lessons.

Acceptance rules

  • R0 validity: no run ends as a measurement-system failure (HARNESS) after one rerun.
  • R1 no regression: every check that passes on a control case under the current version also passes under the candidate.
  • R2 improvement: the candidate passes strictly more development-case checks.
  • R3 held-out: the candidate passes at least as many held-out checks.
  • R4 time: the candidate's total wall-clock time is at most 1.5 times the current version's.

Cases come in three sets of two: development (D1, D2), held-out (H1, H2), and control (P1, P2). Only development-case evidence enters define, analyze, or any prompt the improvement agent sees. Held-out and control results are used only by code.

Since exp2, the improve phase is shown the earlier proposals with their development-case outcomes (proposal history), and since commit 1ba48c8 it also sees proposals the validator refused.

Why these indexes

  • Unique (run_id, seq) on events. Event writes are idempotent: a retry that hits a duplicate key counts as already written, so a run's history never has gaps or doubles.
  • Partial unique index on pinned. The database, not only the code, guarantees that exactly one harness version is pinned. Pinning unpins the old version first. v1 is the pinned version today.
  • Compound indexes on (experiment_id, arm, case_id). Reports, acceptance, and the report's per-arm tables read by experiment and arm.
  • Partial index control_checks. Serves the evaluator's control-history query (control outcomes of a pinned version) without scanning every event. The before-and-after explain is below.

Vector search with a snapshot pre-filter

Each lesson is embedded with BAAI/bge-small-en-v1.5 (384 dimensions, cosine). Roles retrieve the top 3 verified lessons at their first stage through $vectorSearch on lessons_vector, with the filter fields declared in the index:

{ "$vectorSearch": {
    "index": "lessons_vector", "path": "embedding",
    "queryVector": [...], "numCandidates": 100, "limit": 3,
    "filter": { "$and": [
      { "status":   { "$eq": "verified" } },
      { "scope":    { "$eq": "neutralization_brief" } },
      { "snapshot": { "$eq": "M1" } } ] } } },
{ "$addFields": { "score": { "$meta": "vectorSearchScore" } } }

The pre-filter runs inside the index, so a run on memory snapshot M0 cannot see lessons written by a cycle (M1), and unverified root causes are never retrieved. This is what makes the baseline (M0) and memory_only (M1) arms a fair comparison.

The aggregation used by show cost

Token cost per arm, role, and model comes from the recorded model-call events, joined to their run for the arm (python -m adaptive_harness show cost). The $match is served by the run_type index:

[ { "$match": { "run_id": { "$in": [...] }, "type": "model_call" } },
  { "$lookup": { "from": "runs", "localField": "run_id",
                 "foreignField": "_id", "as": "run" } },
  { "$unwind": "$run" },
  { "$group": { "_id": { "arm": "$run.arm", "role": "$role", "model": "$model" },
                "calls": { "$sum": 1 },
                "input_tokens":  { "$sum": { "$ifNull": ["$usage.input_tokens", 0] } },
                "output_tokens": { "$sum": { "$ifNull": ["$usage.output_tokens", 0] } },
                "cache_read_tokens": { "$sum": { "$ifNull": ["$usage.cache_read_tokens", 0] } } } },
  { "$sort": { "_id.arm": 1, "_id.role": 1, "_id.model": 1 } } ]

control_checks explain, before and after

The evaluator's control step reads the recorded control outcomes of a pinned version each time it checks a run:

db.events.find({
  "type": "check",
  "content.control": { "$exists": true },
  "content.version": "v1"
})

The index keys both equality fields, and its partial filter is a predicate the query carries verbatim, so it holds only control-outcome events instead of an entry for every message, model-call, and tool event:

db.events.createIndex(
  { "content.version": 1, "type": 1 },
  { name: "control_checks",
    partialFilterExpression: { "content.control": { "$exists": true } } }
)

Both plans are explain with executionStats on the project's Atlas cluster (MongoDB 8.0.32), run read-only while another experiment was writing, so the collection grew between captures. No control outcome had been recorded yet, so both return no documents; what changes is how much the server reads to find that out.

Before the index, every control check scanned the whole collection, and the cost grows with every run recorded. After it, documents examined equal the number of matching control outcomes, independent of how many other events exist. The time difference is small at this size; the documents-examined count is the number that scales. Source: reports/explain_control_checks.md.

What we learned

  • The same verified lesson across cycles. Each cycle's analyze phase, working from fresh runs, verified the same root cause: E7 on D2, category measurement. The only S7 check was schema, so nothing tested that each race row cites a same-run tool result about that race. Three such lessons are stored, one per cycle.
  • Memory alone did not improve results. The memory_only arm (v1 plus the new lessons) passed 11 development checks in exp1, exp2, and exp3, the same as the baseline without them.
  • Scores vary between identical runs. Under the same v1 configuration, the control cases passed 10, 8, 9, 10, 10, and 10 checks across the six scored v1 arms with control cases in exp1 to exp3 (P1's E2 venue and E3 coverage flipped). This is why R2 compares against the current version run fresh, and why no statistical claim is made.
  • The evaluator refused unproven changes. v2 (venue_match) and v3 (source_agreement) each passed 11 development checks against 11, so R2 failed and v1 stayed pinned. The agent had flagged both as uncertain in its own risk statements. v4 was refused too (below).
  • The operator added the check the lessons asked for, and the harness chose to use it. No editable check tested per-row evidence, so after two cycles the operator added row_evidence to the catalog, off by default, with one S7 repair round. In exp3 the improvement agent, not the operator, proposed enabling it (v4). The acceptance rules rejected v4 on R1 (P1 lost E2 and E3) and R2 (11 against 11). row_evidence passed in all six candidate runs, so the repair round never fired: the check accepts a row with at least one race-specific citation, and the evaluator requires every citation to be race-specific. The check is looser than the measurement it was meant to protect.

Provenance and operator decisions

  • Evaluation data first. 14d7030 (10:40 EDT) committed the cases, definitions, and frozen answer key before any harness code; ecf78b2 (10:42) the quality specification; 703e771 (10:52) the frozen contract. The lanes were then built in parallel against the contract.
  • Optional cases D2, H2, P2. The only default development case, D1, has zero races at its venue, so it cannot exhibit citation defects. The three optional race-audit cases were published in data/cases.json with the defaults, before any harness code, and were used, not added. Every arm covers all six.
  • Budgets raised before the baseline. 1344432 (11:35) set per-case budgets from placeholders of 20 model calls, 40 tool calls, 600 s to 40, 60, 900 s. The first baseline run started at 11:49.
  • row_evidence added to the catalog, off by default, with one repair round. 032720a and f39d1fe, merged as dccd9f1 (13:30), after two cycles verified the same lesson. When an enabled catalog check fails, the S6 role revises once; if checks still fail the run is HOLD. Configurations stored before it keep their hashes. Enabling it is left to the improve phase and the acceptance rules.
  • All code was written on 2026-09-26 with AI coding assistants. The design notes and instructions given to them were written before the event and are not included.

Limits

  • Six fixed cases (two development, two held-out, two control), one run per case per arm. No statistical claim; the models are not deterministic and a repeat could differ.
  • No sigma level or capability index. The control plan uses specification thresholds, not statistical control limits, which need about 20 runs.
  • No candidate has been accepted in exp1, exp2, or exp3; the control phase has not been reached, and v1 is still pinned.
  • A hackathon prototype, not a production system.
